# tron 0.0.0.14

Changes since 0.0.0.13.

- Updated: `tron.php serve --user=<login>` is disabled by default. The shipped `[StdioSettings] AllowLoginOption` is
  now `disabled`, and a missing setting counts as disabled too. `--user` names a user without any token, so whoever
  could start the process could act as any user, an administrator included. stdio now needs a token, like HTTP:
  `TRON_TOKEN=<token>` or `--token-file=<file>`. `serve --user` without a token exits 1 and says why on stderr; a
  token still wins over `--user`. The decision is in `tronStdioIdentity`, tested in `tests/unit/StdioIdentityTest.php`
  (the default, the refusal, an override that enables it, and a token, also over real stdio).
- Updated: `tests/kernel/stdio_smoke.php` reads every page of `tools/list`. A user with more tools than one page
  holds (an administrator on a full installation) had failed its `tron_status` check although the server was fine.

## Upgrade note

An installation that starts `tron.php serve --user=<login>` (an MCP client configuration, a service, a script) stops
working with 0.0.0.14. Before upgrading, either:

- create a token for that user and use it instead of `--user` (recommended):

  ```bash
  php extension/tron/bin/php/tron.php token:create --siteaccess=<sa> --user=<login> --name="<what it is for>" --out=<file>
  # then: tron.php serve --siteaccess=<sa> --token-file=<file>
  ```

  Keep the file 0600 and outside the docroot; `--out` writes it so. Revoke the token when the client goes away
  (`tron.php token:revoke <id>`).
- or keep the old behaviour in `settings/override/tron.ini.append.php`, only where every account that can run
  `tron.php` may act as every user anyway:

  ```ini
  [StdioSettings]
  AllowLoginOption=enabled
  ```

No schema change.
