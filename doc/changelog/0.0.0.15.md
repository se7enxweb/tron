# tron 0.0.0.15

Changes since 0.0.0.14.

## The official MCP PHP SDK

- Added: tron is built on the official MCP PHP SDK ([modelcontextprotocol/php-sdk](https://github.com/modelcontextprotocol/php-sdk),
  package `mcp/sdk`). On PHP 8.2 and newer, with `mcp/sdk` and `nyholm/psr7` installed, the SDK parses and frames every
  message, negotiates the version, keeps the lifecycle, answers `ping` and runs both transports: its `StdioTransport`
  for `tron.php serve`, and its `StreamableHttpTransport` without sessions behind `/tron/mcp`, so the endpoint stays
  stateless for every node of a cluster. tron adds one request handler for `initialize`, tools, resources and prompts;
  tokens, scopes, policies, the audit entry before a write, dry runs, redaction, the journal and the programs are
  unchanged. [protocol.md](../protocol.md).
- Updated: tron's own JSON-RPC and MCP code is now `tronLegacyProtocol`, behind the interface `tronProtocolLayer`. It is
  frozen (security fixes only) and serves PHP 7.4 to 8.1, where the SDK cannot run (it needs PHP 8.2 and runs its
  handlers in Fibers). `[ServerSettings] Protocol=auto|sdk|legacy` (or `TRON_PROTOCOL`) picks the layer; `auto` takes
  the SDK where it can run. `tron.php status`, `tron_status` and the dashboard name the layer in use.
- Updated: where the SDK frames the messages, a few protocol answers differ from the legacy layer: every request before
  `initialize` is refused on stdio (ping included), an unknown method and params that are not an object are -32600,
  batches are refused in every version, an error without a request id has no `id` member, an oversized stdio line is
  dropped and logged, and `initialize` needs `capabilities` and `clientInfo`. Answers above the wire are the same.
- Added: `tests/conformance/official_run.php` runs the official MCP conformance suite against the HTTP endpoint;
  `tests/kernel/protocol_live.php` proves the layer on a real installation over stdio and HTTP. The suite, the PHP
  matrix and the conformance runner run on both layers.
- Updated: composer.json suggests `mcp/sdk` (^0.10) and `nyholm/psr7` (^1.8) rather than requiring them, so an
  installation on PHP 7.4 to 8.1 still resolves. The SDK is Apache-2.0; with it, the combination is distributed under
  the GPL version 3 (README, License).

## Search

- Added: the program `search`: `search_query` (full-text search with filters, sort, paging and facets) and
  `search_index` (the state of the search index) read the installation's search as the calling user, so a result list
  holds only what that user may read.

## Skills

- Added: a skill's `field` or `by` can be a parameter, `$param.<name>`, when that parameter is a string with an enum,
  so one skill counts, filters or sorts by any field the enum lists.
- Added: 26 skills that take as a parameter the value their near-duplicates had built in.
- Removed: 202 skills that differed from another only by a built-in label, lane, kind, day window, priority, class,
  siteaccess, INI file or setting, template, view or module (358 skills before, 183 after). Each answer is proven equal
  to the new skill with the old value as a parameter, on the test world and read only on a real installation. Their
  MCP tools and prompts (`skill_<old name>`) are gone with them; see the upgrade note.
- Updated: `class.containers` takes `containers` true or false and so also answers what `class.leaves` answered.
- Updated: the packs `centre-planning` and `classes-and-schema` 0.0.0.2 require tron 0.0.0.15 (their parameterised
  field and sort keys).

## Command line identity

- Updated: `tron.php call`, `tron.php token:create` and the `tron-skills.php` commands that act as a user (`run`,
  `validate`, `try`, `unit`, `harness --live`) follow serve's rule from 0.0.0.14: a token (`TRON_TOKEN` or
  `--token-file`) decides, and `--user=<login>` without one is refused unless an override sets
  `[StdioSettings] AllowLoginOption=enabled` (disabled by default). `token:create` issues as the token's user: a token
  for that user within the issuing token's scopes, for another user or wider scopes only with `tron/admin`. The first
  token of an installation comes from Setup > tron > Tokens. `call` now also checks `tron/use`. Tested in
  `tests/unit/StdioIdentityTest.php`. The xsh commands `tron:skill:*` pass `--token-file` (xsh.conf `tron_token_file`).

## Upgrade note

- **Command lines.** Anything that runs `tron.php call --user=...`, `tron.php token:create` without a token, or
  `tron-skills.php run|validate|try|unit|harness --live --user=...` (a script, a timer, an `xsh tron:skill:*` call)
  stops working with 0.0.0.15. Give it a token instead: create one in Setup > tron > Tokens (or
  `tron.php token:create --token-file=<an administrator's token> --user=<login> --out=<file>`), keep it 0600, and pass
  `--token-file=<file>`. Where every account that can run these may act as every user anyway, the old behaviour stays
  with `[StdioSettings] AllowLoginOption=enabled` in `settings/override`.
- **Removed skills.** A client, prompt or script that calls one of the removed skills (`skill_<old name>` over MCP, or
  `tron-skills.php run <old name>`) gets "unknown tool" or "no skill". Use the parameterised skill with the old value,
  e.g. `centre.count.by --by lane` for `centre.count.by-lane`; `doc/testing.md`, "Skills dedupe", and the pack pages
  under `doc/skill-packs/` name every replacement.
- **The SDK.** Nothing changes until `mcp/sdk` and `nyholm/psr7` are installed on PHP 8.2 or newer: then `auto` uses
  the SDK. To install them: `composer require mcp/sdk:^0.10 nyholm/psr7:^1.8` (Composer asks whether to allow the plugin
  `php-http/discovery`), regenerate the autoloads (new classes in `classes/protocol/`) and deploy. To stay on the
  legacy layer, set `[ServerSettings] Protocol=legacy`.

No schema change.
