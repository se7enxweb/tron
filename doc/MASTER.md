# MASTER.md: Exponential rules for agents

> These are the Exponential project's own working rules for AI agents, shipped with tron. They come before
> the site's AGENTS.md: **where the two conflict, MASTER.md wins.** A site can replace this file with its own
> copy, or switch it off (see tron's doc/agent-rules.md). Placeholders such as `<ADMIN_PASSWORD>` and
> `www.example.org` stand for the values of your own installation; never write real secrets into a rules file.
>
> Generated by `php extension/tron/bin/php/tron-rules.php sanitize` from the project's AGENTS.md. Do not edit by hand:
> change the source and generate it again, or put a site override in place.

## A published release is permanent

**Every GitHub repository in this project is also a Composer package on
Packagist. A tag, and the release built from it, is immutable the moment it is
pushed. It can never be updated, replaced, re-cut or corrected. Treat every
push of a tag as irreversible, because it is.**

This is not a convention that can be worked around with `--force`. Packagist
reads a tag once and caches the version it found. Even where git will let you
move a tag, anything that has already resolved that version keeps the old
contents, so a "fixed" tag produces two different packages wearing the same
version number — which is worse than the original mistake, and impossible to
diagnose from the outside.

**The rules that follow from this are absolute:**

- **Never delete, move, re-point or re-cut a tag that has been pushed.** Not to
  fix a typo in a message, not to include a file that was forgotten, not to
  rebuild an archive that went out stale. The only correct response to a
  mistake in a published version is to publish the next one.
- **Never edit or replace a GitHub release that has been created.** Adding a
  corrected asset to an existing release has the same effect as moving a tag:
  two different artefacts under one version.
- **Always check what is already published before choosing the next version
  number.** At the start of every release cycle, list the existing tags and the
  existing releases, and pick the next number from what is actually there — not
  from memory, not from what the previous task in the same session used, and
  not from the working tree. A number that looks free may already be taken by a
  release that a previous cycle pushed.

  ```bash
  git fetch --tags
  git tag -l 'v*' --sort=version:refname | tail -5    # never plain `tail -1`
  gh release list --limit 10
  ```

  A plain lexical sort gets this wrong — see **Release Versioning** below. Use
  `--sort=version:refname` or `sort -V`, and cross-check against
  `gh release list`, because a tag can exist without a release and a release
  can exist for a tag that the local clone has not fetched.

- **Verify before you push, not after.** A tag is cheap to get right and
  impossible to correct. Before pushing one, confirm the working tree is clean,
  the test suite passes, and any committed build artefact matches its sources.
  The cost of one extra check is a minute; the cost of skipping it is a version
  number burned forever and a release that cannot be withdrawn.
- **If a bad version does get published, do not try to undo it.** Leave it in
  place, publish the next version with the fix, and say plainly in that
  version's notes what was wrong with the previous one. Consumers pin ranges
  that will pick up the new one; nobody is helped by a hole in the history.

## Source control rules

- **Do NOT make commits in the root project repository. Ever.**
  - All changes must remain as uncommitted work in the working tree / index.
  - Never run `git commit`, `git merge`, `git tag`, or create branches in the root project unless explicitly asked by the user.
  - Never push to origin or rewrite published history in the root project.
  - The user owns the commit history and will review and commit changes themselves.
- **Never add a root-directory `*.md` file to the repository unless the user asks for that file by name.**
  - Only the root `*.md` files **already tracked** may be committed, and only changes to
    them: `git ls-files '*.md' | grep -v /` lists them. A root `*.md` that is not in that
    list is never staged — not by `git add -A`, not by `git add .`, not "by convention",
    not because a wave's story "belongs in the root". Stage files by name.
  - Before every root-repo commit, check: `git diff --cached --name-only --diff-filter=A | grep -E '^[^/]+\.md$'`
    must print nothing.
- **Do NOT credit AI agents or assistants in commit messages. Ever.**
  - No `Generated with [Devin](...)` footer.
  - No `Co-Authored-By: Devin ...` trailers.
  - No mention of AI, agents, bots, or automation tools in the commit title or body.
- **Always write `Exponential`, never the former product name, in a commit message.**
  - This is the same rule the Conventions section applies to code, class names,
    documentation and Markdown, and it applies to commit messages for the same
    reason: the product is called Exponential, and a message is the part of the
    history a reader sees first.
  - Replace every spelling of the product's former name (in any capitalisation, with or without a version or
    "legacy" after it) with `Exponential`, or `Exponential 6.x` where the message really is about this major line.
  - `eZ` on its own is *not* covered and must not be rewritten. It is the
    prefix of real kernel identifiers — `eZContentObject`, `eZINI`, `eZDB`,
    `eZPersistentObject`, `eZHTTPFile` — and a message that renames those is
    wrong about the code it describes. The same goes for `ez` in a real path
    such as `bin/php/ezcache.php`. Rename the **product**, never a symbol or a
    filename.
  - This applies to the commit title, the body, tag messages, release notes and
    pull request descriptions alike, including a message being written on
    behalf of an upstream author whose text used the old name.
  - **Check before committing, not after.** A message is far cheaper to get
    right than to rewrite: rewriting one that has already been published moves
    every commit after it, and if a release tag points into that range the
    choice becomes either breaking a published version's immutability or
    leaving the tag stranded off the branch. Both are worse than reading the
    message once.
- Commit messages must describe the **why** and **what** of the change, written as if authored by the human team.
- Use the following prefixes in commit messages so the changelog can be assembled from history:
  - `Added: <short description>` — new feature, file, extension, class, or capability.
  - `Updated: <short description>` — changed/improved existing behavior, template, INI, class, or service.
  - `Removed: <short description>` — deleted feature, file, class, extension, or dependency.
  - `Renamed: <short description>` — renamed file, class, extension, setting, or block.
- Do not combine multiple change types in one commit if they can be split. If a single change touches many areas, list each on its own line in the commit body.
- Do not rewrite published git history (`git rebase --interactive`, `git push --force`, etc.) unless explicitly approved.
- Do not commit credentials, keys, `.env`, `local.properties`, or `settings/site.ini` overrides.
- Do not modify repository security policies (`.htaccess`, `vhost_ssl.conf`, `php.ini` hardening, `.npmrc`, `composer` trust) to work around CI or build failures — escalate to the user.

## Build and run

- **Deploy a PHP change with one command: `exp:velocity deploy`.** It runs every step below in
  the right order, prints PASS/FAIL/SKIP with the time of each, stops at the first failure and
  exits non-zero:
  ```bash
  ./console exp:velocity deploy --dry-run --allow-root-user   # what it would do, nothing else
  ./console exp:velocity deploy --allow-root-user             # the usual case
  ./console exp:velocity deploy --kernel --allow-root-user    # a kernel class was added or renamed
  ```
  Steps: extension autoloads (`--kernel`: kernel autoloads too, `kernel/` and `lib/` only) ->
  `--clear-tag=ini` -> template, template-override, translation, design_base caches -> engine archive
  (rebuilt only when a file in `kernel/`, `lib/` or `autoload/` changed; every file parsed first,
  so a broken file stops the deploy before any service is touched) -> `systemctl reload` of the
  PHP-FPM found by `[DeploySettings] PhpFpmService` (`auto` finds `<PHP_FPM_SERVICE>` here) ->
  Velocity restart -> content, exphttpcache, (`--packer`: ezjscore-packer,) template-block caches -> Velocity's response cache.
  Skip steps with `--no-autoload`, `--no-fpm`, `--no-velocity`; `--rebuild-phar` forces the
  archive rebuild; `--packer` also clears the packed scripts and styles, always right before template-block (use it when an ezjscServer_* function or its settings changed). Docs: `doc/bc/6.0/velocity-engines.md` ("Deploying a PHP change").
  - `exp:velocity restart` on its own now skips the ~26 s archive rebuild when nothing in the
    archive changed ("engine.phar is current, not rebuilt"); `exp:phar check` says whether it is.
- **Always use `php -l` as the canonical compile check** before doing anything else with a touched `.php` file.
- **Template cache is disabled** in the active setup, so edits to existing `.tpl` files are reflected instantly. Only run `php bin/php/ezcache.php --clear-all --allow-root-user` when a new template path is introduced, an INI/class changes, or a rendered result looks stale.
- **Always clear all caches after INI, class, or YAML changes:**
  ```bash
  php bin/php/ezcache.php --clear-all --allow-root-user
  ```
- **Restart PHP-FPM after class/INI changes so the web runtime sees them:**
  ```bash
  systemctl restart php-fpm
  ```
- **Ask for explicit user approval before running destructive commands** such as `rm`, `DROP TABLE`, bulk cache wipes, `git checkout` over uncommitted work, `git reset --hard`, or `php bin/php/ezcache.php --clear-all` on a production environment outside the normal workflow.
- **Run a smoke test after every non-trivial change:** `webfetch https://www.example.org/` or `curl -s https://www.example.org/ | head -20`.
- `php bin/php/ezexec.php <relative-path-to-script.php> --allow-root-user` is the canonical way to run PHP with the eZ bootstrap on this box.
- `local.properties` or `.env` files are ignored by Git; never commit them.
- `settings/override/site.ini.append.php` and `settings/override/sevenx_*.ini.append.php` may contain secrets; never commit the `override/` tree.

## Release versioning

- **A version at `.9` goes to `.10`. Only the last octet increments; the
  positions above it do not move.**
  - `0.0.4.9` -> `0.0.4.10` -> `0.0.4.11`. Never `0.0.5.0`.
  - There is no "running out" of digits. The last position is an integer and
    keeps counting. Moving any position above it is a deliberate decision about
    what the release means, taken by the user, and never a consequence of
    reaching nine.
  - This applies to every package here, not only the web server.
- **Verified, not assumed.** `v0.0.4.10` was released on 2026-09-22 and both
  Packagist and GitHub order it after `v0.0.4.9`: Packagist normalises and
  compares each position numerically, and GitHub Releases orders by the tag's
  date rather than its name.
- **`~` in `composer.json` already allows it.** The tilde floats the last
  position, so `~0.0.4.9` means `>=0.0.4.9 <0.0.5.0` and `0.0.4.10` is inside
  it. Repin at release time for clarity, not because the old constraint would
  have blocked the install.
- **A plain lexical sort gets this wrong**, and that is the one real trap.
  `0.0.4.10` sorts *before* `0.0.4.8` by name:

  ```bash
  git tag -l 'v0.0.4.*' | tail -1                 # v0.0.4.9   WRONG
  git tag -l 'v0.0.4.*' --sort=version:refname    # v0.0.4.10  right
  git tag -l 'v0.0.4.*' | sort -V | tail -1       # v0.0.4.10  right
  git describe --tags --abbrev=0                  # right, follows commits
  ```

  Any script that picks "the newest tag" by name needs `--sort=version:refname`
  or `sort -V`. Composer and Packagist are unaffected.

## Extension releases carry their version in ezinfo.php and extension.xml

Owner rule (2026-09-28), a convention for managing the system through extension
packages: **every release of an extension raises the version number inside the
extension to exactly the release's version, in the same release.** The about page
(`/ezinfo/about`), the upgrade checks and anyone reading an installed copy must be
able to tell which release they are looking at from the files alone.

- **`ezinfo.php`**: `'Version'` equals the release version (without a `v` prefix:
  tag `v6.0.8` -> `'Version' => "6.0.8"`). Keys are quoted strings, `info()` is
  `static`, the class is `<extension>Info`. It also states `Name`, `Copyright`,
  `License` ("GNU General Public License v2.0 (or any later version)" for GPL code,
  or exactly what the extension's LICENSE says) and `Info_url`
  (`https://github.com/se7enxweb/<repo>`).
- **`extension.xml`**: `<metadata><version>` equals the same number, never
  `//autogentag//` or `dev-master`; `<license>` and `<info_url>` as above.
  The about page reads `extension.xml` first when it has `<metadata>`, so both
  files must agree.
- **Other version fields** the repo keeps (a `version` in `composer.json`, a
  version header in an extension's own `share/filelist.md5`) move with it.
- **One commit before the tag**: bump the fields in a commit ("Updated: Version
  <x>" or as part of the release's last commit), then tag that commit. Never tag
  first and bump afterwards: the tag would carry the old number, and tags are
  permanent (see "READ FIRST").
- **Choose the number first** exactly as "Release Versioning" says (check tags with
  `--sort=version:refname` and `gh release list`, last position counts on), then
  write it into the files.
- **Extensions shipped inside the kernel repo** (ezjscore, ezoe, ezformtoken ...)
  carry the Exponential version they ship with (e.g. `6.0.15`).

## Changelog and commit format

- Changelogs are required for every commit that reaches a port milestone or changes a package's port status.
- When a version is cut, create or update `doc/changelogs/<version>.md` (e.g. `doc/changelogs/1.0.2.md`) before the build is considered shipped.
- Review `git log` since the previous version and rewrite each change into one of these four categories:
  - `Added: <short description>` — new feature, screen, endpoint, file, extension, class, or capability.
  - `Updated: <short description>` — changed/improved existing behavior, template, INI, API, class, or service.
  - `Removed: <short description>` — deleted feature, file, endpoint, dependency, class, or permission.
  - `Renamed: <short description>` — renamed file, view, class, endpoint, extension, build target, or setting.
- Commit messages that affect the changelog should use the same prefix so the changelog can be assembled from commit history:
  - `git commit -m "Added: ..."`
  - `git commit -m "Updated: ..."`
  - `git commit -m "Removed: ..."`
  - `git commit -m "Renamed: ..."`
- Do not combine multiple change types in one commit. If a change adds, updates, and removes things, split it into separate commits or list each on its own line in the changelog.
- Keep descriptions human-readable and avoid AI/agent attribution.

## Database gotchas

- `eZDB::query()` returns `true`/`false` for most DML/DDL.
- **Do not rely on `SET @var := ...`** in `eZDB::query()` — it returns `false` and fails silently.
- For multi-step inserts that need `LAST_INSERT_ID()`, prefer `eZPersistentObject` (`->store()` and `->attribute('id')`) over SQL variables.
- Always escape strings with `$db->escapeString()` before interpolating SQL.
- Always cast identifiers to `(int)` before interpolating numeric SQL fragments.
- `eZPersistentObject::fetchObjectList()` is the preferred way to query custom tables.

## Autoloading

- New classes in `extension/<ext>/classes/` are not always picked up immediately; run `php bin/php/ezpgenerateautoloads.php -e`.
- In CLI scripts and module views, use `require_once __DIR__ . '/../../classes/<classfile>.php';` to load helpers if autoload fails.
- Naming convention: class `ExpFoo` maps to file `sevenxfoo.php`; class `expLayoutsFoo` maps to `explayoutsfoo.php`.

## Conventions

- Follow existing eZ legacy style: camel-case `expLayouts*` classes, Smarty templates, `eZPersistentObject` patterns.
- **Never use `Ibexa` in code file names or class names.** Use the `Exp` (Exponential) adapter prefix for all upstream Ibexa-branded packages.
- **Never use the product's former name in code file names, class names, documentation, or Markdown.** Use the `Exp` (Exponential) project name where needed.
- New PHP files must start with `<?php` and use CRLF-free line endings.
- Prefer `public static` for stateless helpers; prefer instance methods for classes that wrap configuration or eZ objects.
- `eZINI::instance('explayouts.ini')` is the canonical way to read extension settings.
- `eZDebug::writeNotice()`, `eZDebug::writeError()`, `eZDebug::writeWarning()` are the canonical debug output methods.
- Avoid `emojis`; keep UI copy concise.
- Do not commit credentials or modify security settings to bypass CI/build failures.

## Admin design and template styling rules (VERY IMPORTANT)

Owner rule (2026-10-14). Why: admin4 had drifted to 55 templates with their own inline `<style>` block
(7,831 lines, 35 private custom-property prefixes, utilities copied up to 41 times, four different accent
colours, 46 blocks hard-coding white with no dark mode). design/admin had 58 more. All of it came from
earlier agent work that styled each new page on its own. These rules apply to **every admin design**
(admin, admin3, admin4, admin4l and any new one) and to design work in templates generally, including
extension designs (exp_adminui and the rest).

- **No `<style>` block and no `style=""` attribute in a template. Ever.** All CSS lives in the design's
  `stylesheets/` directory and is loaded through `[StylesheetSettings]` (design.ini / the siteaccess), so the
  ezjscore packer bundles and caches it. The only exception is a minimal pre-paint guard in the pagelayout
  (e.g. the theme flash guard), documented in place with the reason.
  - Values that really are per-element data (a computed width, a progress percentage) go in a `data-*`
    attribute or a CSS custom property set from a stylesheet class, never in `style=""`.
- **Reuse the shared component classes before writing any CSS.** In admin4 that is
  `design/admin4/stylesheets/components.css`: `.a4-card`, `.a4-tag`/`.a4-badge`, `.a4-btn`, `.a4-table`,
  `.a4-toolbar`, `.a4-filterbar`, `.a4-sr-only`, the reset and the focus ring (`.a4-page`). design/admin has an identical copy of
  components.css (the test keeps the two equal), next to the admin classes (`box-header`, `block`, `button`). Add a new shared component centrally only
  if nothing fits; **never copy one into a module**.
- **Colours, radius, spacing and fonts come only from the design's tokens** (`--a4-*` in admin4). No
  hard-coded values (`#fff`, `#c2410c`, `12px`), and no local token aliases (`--rl-ink`, `--rad-card` ...).
  There is one accent token and one radius token; do not introduce another.
  - **Every new token gets a value for `html[data-a4-theme="dark"]`** in the same commit.
- **Module-specific CSS is the exception.** It goes in a central file,
  `stylesheets/modules/<group>.css` (setup, content, people, structure, workflow; design.ini
  `AdminComponentCSSFileList`), uses `.a4-<module>-*` class names, and holds only
  what the shared components cannot do. One neutral prefix per design; no per-module scope prefixes like
  `.exp-roles`, `.nf-`, `.cb-`, `.shop-`.
- **Check every new or changed admin page in light AND dark mode**, at 1440px (scale 1) and 960px at scale 2
  (the owner's 200% zoom). No white card on a dark background, text contrast at least 4.5:1, no horizontal
  overflow, no console errors.
- **CSS changes reach the browser through the packer.** After a stylesheet change: deploy with `--packer`
  (template-block cache too), never add `?v=` or other version queries to links (owner rule), and tell the
  owner to hard-reload if a browser still shows the old file.
- **Enforced in CI:** `tests/tests/design/AdminStylingRulesTest.php` (DB-less, testsuite `design`) fails on any `<style>` block or
  `style=""` attribute in the templates of every admin design (outside its shrinking ALLOWLIST), on hard-coded colours or radii in `stylesheets/modules/*.css`,
  and on a token without a dark value. Never weaken it or add an allowlist entry to make a change pass; fix the
  template instead.
- **Code review checklist for any template change:** no inline CSS; shared classes reused; only tokens; dark
  values for new tokens; module CSS in `stylesheets/modules/`; light and dark screenshots checked; packer
  deploy done.
- Contributor documentation: `doc/bc/6.0/admin4-styling.md` (the component and token API).

## File removal

- Never use `rm` or any destructive file removal without explicit user approval.
- If file cleanup is genuinely needed, describe exactly what will be deleted, wait for confirmation, and only then use the appropriate skill or command.
- Do not run `git checkout -- <file>` over uncommitted changes without user approval.

## Verification checklist

Before declaring a PHP class/port task complete:

1. `php -l` for every touched `.php` file.
2. `php bin/php/ezpgenerateautoloads.php -e` to refresh the autoload array.
3. `php bin/php/ezcache.php --clear-all --allow-root-user` to clear stale caches.
4. `systemctl restart php-fpm` so the web runtime sees the changes.
5. Smoke test the front page `https://www.example.org/`.

## Security notes

- The admin and API URLs are discoverable; security is enforced server-side, not by obscurity.
- Do not commit `.env`, `composer.*`, `vendor/`, or `settings/override/*`.
- `.htaccess` / `vhost_ssl.conf` should return 403 for `.env`, `.git/`, `src/`, `config/`, `vendor/`, and `composer.*`.
- `APP_ENV=prod` and `APP_DEBUG=0` on any Symfony backend.
- Response headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Content-Security-Policy`) are set server-side.
- Do not disable or weaken `php.ini` / `.htaccess` security settings to work around a build failure.
